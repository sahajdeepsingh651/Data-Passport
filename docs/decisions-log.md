# Data Passport — Decision Log

> Standing rule for this project: every architectural or design decision, and the reasoning behind it, gets recorded here (or in the most relevant doc) as it's made — not reconstructed later from memory.

| Date | Decision | Reasoning | Alternatives considered / rejected |
|---|---|---|---|
| 2026-08-07 | Data architecture: lightweight medallion lakehouse (Bronze → Gate → Silver → Gold) | The layer transitions map directly onto the "passport control" metaphor — knowledge flows freely, PII/credentials get caught at the Bronze→Silver gate. A warehouse loses unstructured knowledge (schema-on-write too rigid for chat logs/decisions); a plain lake has no natural governance checkpoint. | Data warehouse only (rejected — too rigid for raw knowledge). Pure data lake (rejected — no gate for PII/governance). Full lakehouse with Iceberg/Delta + Spark/Trino (rejected — too much setup risk for a hackathon time budget). |
| 2026-08-07 | Storage: Bronze = folders/MinIO object storage; Silver/Gold = single PostgreSQL instance + `pgvector` | Keeps the VM to one database service while still delivering real semantic search for the demo. | Separate dedicated vector DB (Qdrant/Chroma) alongside Postgres — rejected as more moving parts than the team/timeline can support. SQLite — considered but weaker "enterprise" story for judges. |
| 2026-08-07 | Serving layer: MCP server (`search_knowledge`, `record_insight`, `announce_task`, `get_agent_activity`, `handoff`) + web dashboard | Gives any connected AI agent, anywhere in the org, the same access — directly demonstrates "no agent can pick up where another left off" being solved. Dashboard gives judges a visual proof point (redaction audit log, live agent activity). | — |
| 2026-08-07 | Hackathon prototype scope narrowed to: knowledge capture & search + shared agent activity visibility + PII/credential guardrail | These three together demonstrate the theme directly: "knowledge that should move doesn't, and data that shouldn't move does." Contradiction detection explicitly deferred. | Full scope (contradiction detection, cross-team conflict alerts) — deferred, not rejected; revisit if time allows. |
| 2026-08-07 | Session extraction schema: envelope (universal) + core content (universal) + domain-specific extension payload (namespaced per department) | Keeps the shared schema generalizable enough for org-wide search while letting each department capture what's actually useful, without forcing a lowest-common-denominator shape on everyone or letting one department's quirks leak into the shared schema. | Single flat schema for all departments (rejected — either useless-generic or unusably narrow). Fully separate per-department schemas with no shared layer (rejected — breaks cross-team search entirely). |
| 2026-08-07 | Context bus event = compact projection (id, summary, status, `gold_ref` pointer), not the full record | Keeps bus messages small and fast; consumers fetch full detail from Gold on demand. Standard notification-plus-pointer pattern rather than event-carried-state-transfer. | Carrying the full record on the bus — rejected, unnecessary payload size for most consumers. |
| 2026-08-07 | Controlled vocabulary strategy: `outcome` = hard enum; `department` / `entity.type` = soft-suggested list + Gate-side normalization (exact/synonym match → embedding-similarity fallback → unmatched terms queued for human review) | `outcome` is a small, closed taxonomy that doesn't need to grow. `department`/`entity.type` are genuinely open-ended over time; a hard enum would block legitimate new categories and create per-team drift if left fully free-text. Capture must never be blocked on vocabulary purity — unmatched terms still flow through, tagged `unverified`. | Fully static enum for all three fields (rejected — too rigid, requires redeploying to every agent on change). Fully free-text with agents inventing synonyms ad hoc (rejected — no shared source of truth, teams' vocabularies drift apart instead of converging). |
| 2026-08-07 | Vocabulary/synonym data served to agents via an ISR-style cache (precomputed snapshot, background revalidation) rather than a live query per tool call | Keeps MCP tool-call latency low while still letting the vocabulary evolve after Gate-side curation — same stale-while-revalidate tradeoff as ISR in a search index. | Synchronous DB lookup per request (rejected — unnecessary latency on every agent tool call for data that changes infrequently). |
| 2026-08-07 | Added a second checkpoint, the **Egress Gate**, at the endpoint device — blocks/redacts PII and confidential business data (financial/pricing docs, price figures) before it leaves toward any *external* AI; local/on-prem LLMs are exempt | Protects the org's data leaving to third-party AI, not just knowledge entering the shared passport — the other half of "data that shouldn't move, moves." Local LLMs are trusted because the data never leaves org infrastructure. | Doing PII/confidential-data control only at the Ingestion Gate (rejected — that only protects the passport's own knowledge base, not general shadow-AI usage across the org). |
| 2026-08-07 (PROPOSED, not confirmed) | Egress Gate interception mechanism: leaning toward a local network proxy/agent (TLS interception of outbound HTTPS to AI endpoints) for broadest coverage | Catches browser, desktop app, and CLI traffic through one control point rather than one integration per tool. | Browser extension only (narrower coverage, but far less setup risk). IDE/CLI plugin only (narrowest, most reliable). Decision documented in full with trade-offs in `data-passport-security-egress.md`; team recommended timeboxing a TLS-interception spike before committing, given hackathon time constraints. |
| 2026-08-07 (RESEARCH, not yet adopted) | Reviewed Glean's architecture for applicable ideas: typed/validated `domain_data` fields (reject at Gate on type mismatch), entity extraction linked to a canonical registry (not just freeform tags), a third ingestion path for context that's used but never indexed, and hybrid ranking (vector similarity + our existing `links[]` relationships) instead of vector-only | Glean is the closest mature analog to this project (enterprise knowledge access + permission-aware retrieval); several of its mechanisms map directly onto open gaps in our schema (`domain_data` validation was previously undefined; entity linking wasn't decided). Full findings and per-idea recommendation in `glean-research.md`. | Not copying: separate graph database, custom per-cloud embedding model training, full ACL mirroring from every source system — all out of scope for hackathon time. |
| 2026-08-07 | Adopted from Glean research into the live docs: (1) `domain_data` fields now require a declared type per field, validated at the Gate with a rejection error on mismatch (`data-passport-schema.md` §4.0); (2) `entities[]` gained an optional `ref_id` for future canonical-entity-registry linking; (3) Gold-layer ranking is hybrid — vector similarity plus a boost from `links[]` relationships, not vector-only (`data-passport-architecture.md` §Gold) | These closed concrete gaps the schema previously left undefined (validation mechanism, entity linking) using a proven mechanism from a mature product, at no extra build cost — the ranking boost reuses the `links[]` field we'd already designed rather than requiring a new data structure. | Building a canonical entity registry now (deferred — `ref_id` stays unused until the registry exists). Building a separate graph database for relationship signals (rejected — `links[]` in Postgres is enough for hackathon scope). |
| 2026-08-07 | Left the "ingestion paths" question (should some agent context stay ephemeral, never hitting Silver/Gold) as an open, explicitly flagged question rather than deciding it now | Adopting it without a build-cost/benefit discussion with the team risked scope creep during a hackathon; better to surface it than assume either answer. Flagged in `data-passport-architecture.md` § "Not every ingestion path needs to hit Silver/Gold." | — |
| 2026-08-07 | Reverted two of the three Glean-adopted changes: dropped `entities[].ref_id` (schema `1.1.0` → `1.1.1`) and reverted Gold-layer ranking from hybrid (vector + `links[]` boost) back to plain vector similarity | Both were copied because "that's what the mature product does" without checking fit for our scale/timeline. `ref_id` points at an entity registry we're not building — unused speculative field. Hybrid ranking solves a relevance problem that only appears at Glean's scale (billions of docs); at hackathon data volume (tens–low hundreds of records) plain vector similarity already surfaces the right result, and building/tuning a scoring formula would spend build time on a problem the demo doesn't have. Kept the third adopted change (typed `domain_data` validation, §4.0) — that one closed a real, pre-existing gap at negligible build cost, independent of scale. | Both moved to "Future work" sections in `data-passport-schema.md` and `data-passport-architecture.md` rather than deleted outright — worth revisiting post-hackathon if the knowledge base or entity-linking need actually materializes. |
| 2026-08-07 | Egress Gate & Ingestion Gate policy configuration model: admin sets a mandatory floor (destinations/categories/session-types that are always checked or always captured); employee choice can only extend that floor, never shrink it | Pure system-decides-everything removes employee trust/buy-in (a device agent that silently wiretaps everything is a hard sell even internally) and pure employee-decides-everything undermines the "foolproof" goal (the at-risk person could simply not select the risky app/category). The admin-floor/employee-ceiling shape gets both: non-negotiable minimum where it matters, real choice everywhere else. Documented in `data-passport-security-egress.md` §3. | Fully system-controlled (rejected — no employee buy-in). Fully employee-controlled (rejected — defeats the security goal). |
| 2026-08-07 | Resolved the previously open "ingestion paths" question using the same admin-floor/employee-ceiling model: a session becomes a Silver/Gold record only if `record_insight` is called — automatically for admin-mandated categories, or by the employee's own explicit choice otherwise. Added `consent_basis` and `consent_actor` fields to the schema envelope (`1.1.1` → `1.2.0`) | Answers, with a concrete mechanism, the question left open in `data-passport-architecture.md` after the Glean research pass ("should some agent context stay ephemeral, never hitting Silver/Gold?") — yes, and consent is the deciding factor, not a separate ephemeral/permanent path. Reuses the existing `record_insight` call as the consent action instead of adding new machinery. | Automatic capture of everything (rejected — no employee consent, and not what was asked for). A separate ephemeral-context storage path per Glean's "Context Provisioning" (rejected — consent-gating the existing pipeline is simpler and reuses what's already built). |
| 2026-08-07 | Moved PII/credential detection & redaction fully to the endpoint device — no longer a central-server responsibility. One shared on-device engine now gates both outbound flows: toward Data Passport's own ingest API (always redact, no exceptions) and toward any external AI (existing Egress Gate policy, `data-passport-security-egress.md` §2). Central Bronze/Gate no longer scans for or redacts PII; it receives already-clean content and trusts the endpoint's self-reported `sensitivity_flags` metadata (counts/categories only, never raw values) for the audit trail. Also decided: **no server-side PII verification scan** — the central system fully trusts the endpoint, by design | PII must never leave the device at all — not to Data Passport's own server, not to any AI — full stop; a central server that receives and redacts raw PII is itself a liability and contradicts that guarantee, even though the earlier design only intended it as "internal, already governed" storage. Skipping server-side verification keeps the privacy claim structurally true ("we never receive it, so we can't leak it — not even to our own admins") rather than merely policy-enforced | Server-side verification/defense-in-depth re-scan on arrival (considered and explicitly rejected — the team chose the stronger, simpler trust boundary over a safety net; accepted trade-off: no central backstop if an endpoint's detection is buggy, outdated, or bypassed). Keeping redaction centralized at the Bronze→Silver Gate as originally designed (rejected — outright violates the "never leaves the device" requirement, since raw PII would have to reach the server to be redacted there). |
| 2026-08-07 | PoC build order narrowed to the core service only — ingest API → Gate → Silver/Gold → Context Bus → serving (REST + MCP + SSE), defined concretely in `data-passport-core-service.md`. Origin-side capture and destination-side consumption mechanisms (browser extension / network proxy / IDE plugin / manual — `data-passport-security-egress.md` §4–5) are explicitly deferred to the team and decoupled from the core via a plain HTTP contract (`POST /v1/ingest` in, `GET /v1/search`\|`/v1/agent-activity`\|`/v1/handoff`\|`/v1/bus/subscribe` out) | Lets the still-undecided endpoint mechanism be chosen and built in parallel without blocking the core, and keeps the core independently demoable (curl/Postman/a basic MCP client) before any endpoint software exists — same de-risking logic already used for the Egress Gate's Option D (one shared policy engine, interceptor swappable). Also turns the previously-named-but-undefined "Context Bus" into a concrete mechanism: a Postgres table for durability plus `LISTEN`/`NOTIFY` for real-time push, no new infrastructure. | Building an endpoint-side mechanism first (rejected — it's the biggest unresolved unknown; would block core progress on an undecided dependency). Building both halves simultaneously with no defined interface between them (rejected — risks the two not composing cleanly once the endpoint mechanism is finally chosen). |
